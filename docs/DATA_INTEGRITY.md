# Data integrity

The original Beta contains historical user data. Do not write to, reset, migrate, export into Preview, or clear its local storage without explicit authorization. Do not remove an installed app or change its package/signing identity to work around an update problem. Treat backups and signing material as private and never commit them.

- Raw segment timestamps and durations are authoritative. Today clips them to the local day and aggregates milliseconds before formatting. Unique coverage is the union of intervals; total is their sum; overlap is total minus unique. Unlogged is elapsed minus unique, and remaining is local-day end minus now. Local day length may be 23 or 25 hours.
- A pause is not active recorded time. Concurrency shorter than one minute may be omitted from warnings, but remains in raw totals. Never delete original overlapping records automatically.
- Gap logging validates the selected original interval against the latest unlogged boundaries immediately before the existing manual save. The unchanged displayed endpoints retain their exact original milliseconds. Edited endpoints must be within the gap. Failed persistence retains prior records.
- Explicit category choices take precedence; empty choices permit recognition. Synthetic/ambiguous names are not guessed. The original built-in Preview example set is identified from its complete known fixture signature without rewriting it; its new generator carries explicit labels. Preview sample evidence is excluded from category analytics and fitness goal evidence where those paths are used.
- V252 review uses the existing auditable save bridge; timestamp correction is limited to eligible records and keeps an audit event. Do not replace a multi-segment history with a fabricated single interval.
- Plan recovery excludes identified sample plans and timers, duplicate linked session IDs, and future-dated finished timers from evidence. Duplicate identifiers affecting the review period, and missing or unsupported identifiers on plans in that period, block recovery review with a backup-and-review message; they are not silently repaired. An unverified plan is not treated as missed. A recovery decision requires a preview and in-app consent; its source and conflicts are rechecked after consent, and the original plan and tracked history are retained. A recovery booking is a future plan, not a completed activity.
- Marking a plan skipped is a separate, explicit user decision. The reviewed plan is rechecked after in-app consent, saved through the existing atomic checkpoint and given an audit entry; the original plan remains and no tracked activity is created. Ambiguous identifiers, intervening edits and failed checkpoint writes leave it unchanged.
- Repeated plans require an occurrence preview and explicit in-app approval. The previewed occurrence fields are compared again after approval, conflict checks use the current workspace, and the whole series is saved through one atomic checkpoint. A changed form, intervening conflict, repeated series identifier or failed save cannot silently add a partial series.
- The integrated Plan task editor verifies the saved task array in the canonical checkpoint as well as the core activity records. If a write returns but its task data cannot be verified, the editor reports that state and prevents a blind retry; it does not claim the task was safely verified.
- Local recovery uses the atomic checkpoint and journal. A browser reload test establishes only local persistence, not server durability, device backup, or two-device synchronization.
- Opening or reloading nutrition must not insert illustrative targets into the workspace or create a sync operation. A previous build could fill missing target fields and mark the settings with `exampleComparisonPreset`; retain existing values and provenance because the application cannot determine which individual fields the user chose. Nutrition and Insights identify such comparisons as potentially containing examples. Only an explicit user save changes settings.
- Starter-data repair and removal must refuse when an untagged record refers to a generated record, including nested ID-shaped links and duplicate identifiers. This conservatively prevents a repair from altering or deleting linked user records, and avoids leaving them orphaned after sample removal. No automatic unlinking is performed. The check applies to the known generated batch and recognized ID-shaped links; it is not a general integrity proof for every possible imported schema.

Preview startup logs on 26 November 2026 reported SQLite configured by `LIFEOS_DB`; the service description did not show a persistent disk. Do not rely on its server-side data surviving redeploys until persistence is independently established. The separately named disposable staging PostgreSQL instance was available and listed with expiry **8 December 2026 06:15 UTC**; its connection to any service was not established. No database was queried or modified for this observation.

In a disposable PostgreSQL rehearsal, a calendar decision and a regular workspace write could both previously report success at the same revision, overwriting one result. The calendar transaction now locks existing state and conditionally inserts or updates its revision, returning a conflict for the losing writer. Tests cover both existing and initially absent state. This fix has not yet been deployed to Preview. The state-only server JSON export omits preferences, calendar audit and calendar authorization; it is not a full database backup.
