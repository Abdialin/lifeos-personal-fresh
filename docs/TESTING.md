# Testing and evidence

All browser fixtures in `tests/today-v250*.cjs`, `tests/plan-overview.cjs` and `scripts/capture-design-baselines.cjs` intercept requests: local repository assets are served to an isolated Preview-origin browser context, and other requests are blocked/fulfilled offline. They never need a real account or user history.

`tests/authenticated-isolated-v1.cjs` is different: it starts a temporary local Python server with a new random login and sync token and a new temporary SQLite file, blocks nonlocal browser requests, and uses real login, recovery and sync HTTP endpoints with synthetic records. It verifies the recovery downloads before explicitly restoring the fixture, then exercises a partial gap, History, a task change, server readback and reload. It also simulates an empty server response for a populated device, first with pending changes and then after the queue has been acknowledged; it checks that loading and stale uploads do not replace the local workspace or write to the simulated empty server. The real temporary server remains intact during that simulation. It captures all current primary tabs in dark/light when `AUTH_V1_CAPTURE_DIR` is set. The temporary database and files are removed in `finally`. This is not the Render database, a production account, a native-device test or a complete cross-device sync certification. Some behavior guarded by the Preview hostname is not exercised on localhost.

`tests/recovery-reviewed-merge.cjs` intercepts every request and follows the current visible Settings & data recovery controls with synthetic browser records. It checks that an exported checkpoint contains those records but no synthetic token, invalid files do not write, review requires backup confirmation, a workspace changed since review cannot be overwritten, and a re-reviewed merge retains newer local and backup-only activities. An interrupted backup timer is paused for duration review; the merged result survives reload. The test cannot establish that the actual Android document picker worked, that a user's recovery file is intact, or that an old Render database is recoverable.

`tests/sync-uncertain-ack.cjs` uses intercepted synthetic responses through current Settings & data. It verifies that a storage probe is read-only, an unsuccessful atomic acknowledgement keeps the full local journal, and a confirmed prior snapshot is removed without discarding later operations after a simulated interrupted upload and reload. `tests/two-browser-ui-conflict.cjs` signs two browser contexts into a fresh temporary SQLite server, saves one synthetic record offline and another on the server, and checks that stale synchronization retains both rather than overwriting either. It does not exercise a full reviewed UI merge or an actual external service. `tests/nutrition-user-targets.cjs` checks that opening or reloading a fresh workspace does not create illustrative nutrition targets, explicit saves persist, and existing user and previously marked example settings remain unchanged. It checks example provenance in nutrition and Insights views.

`test_starter_data_preservation.cjs` verifies synthetic starter repair/removal leave unrelated records unchanged and refuse untagged linked events, workouts, plans, sessions, nested ID lists and duplicate IDs. `tests/starter-data-safety.cjs` exercises the current advanced Plan UI with intercepted files: explicit confirmation and backup requests for adding, repairing and removing samples, persistence after reload, and refusal without a write when an untagged event is linked to a sample. These fixtures do not open any real backup or account; arbitrary external schemas and links without recognizable ID names remain unverified.

`tests/insights-history-navigation.cjs` exercises the existing Insights shortcut into the current Track History tab, including a recorded synthetic activity, an empty workspace, light mode and a reduced browser height. It checks that navigation leaves the workspace and atomic checkpoint unchanged. It does not validate all Insights drill-downs or native scrolling.

The shared-theme test changes the preference from Today and Plan, navigates all six sections and reloads. The timer-visibility test covers matching and different concurrent timers, scroll, tabs, expanded controls, overnight day portions and reduced browser heights without editing sessions. The My Life test checks subsection visibility, no repeated general panel, routine control ordering, retained routine-day selection and keyboard focus after refresh without stealing focus from other controls, access to the local challenge editor and legacy sharing, preserved records, both themes, three mobile viewport sizes and WCAG contrast for the visible Fitness/Nutrition headings and nutrition metric text. It is a targeted check, not an audit of every My Life component.

`tests/today-overview-acceptance.cjs` checks individual running/paused activity and future-commitment details, grouping and clipping paused day-part segments, rollback on failed timer saves, reload, empty data, navigation, text contrast and touch sizes. Its optional captures cover all four Today tabs in both themes at 360, 393 and 412 pixels and a 460-pixel height; viewport navigation must settle before each image. `tests/today-timer-clearance.cjs` checks the dedicated Today timer row and clickable actions in each tab, including scrolling, both themes and reduced heights. `tests/track-inline-timer.cjs` also verifies that Track retains its previous floating control and that selected, concurrent and overnight timers remain available. These are synthetic browser tests, not Android keyboard or system-inset verification.

`test_focus_controls_v221_browser.py` tests visible Focus controls, simulated vibration, pause/break accounting, snooze and explicit alarm termination; changed alarm state and rejected storage writes cannot be silently overwritten. `TRACK_ALARM_CAPTURE=1` records the synthetic active-alarm sheet. `test_android_bridge_v222_browser.py` exercises a mocked receiver and checks allowed message fields; neither test verifies native hardware or background delivery.

`test_postgres_persistence_v217.py` and `test_preview_migration_postgres.py` require explicit opt-in and a disposable PostgreSQL server on localhost. They test competing calendar/workspace saves, offline SQLite and state-only JSON validation, a migration into a newly created empty database, rejection and rollback cases, `pg_dump`/`pg_restore` into a separate disposable database and application restart. The GitHub workflow uses PostgreSQL 16; the local rehearsal used PostgreSQL 17. They never connect to Render and do not verify Render redeploys or managed point-in-time recovery. See the [storage runbook](PREVIEW_STORAGE_RUNBOOK.md).

`python3 -m unittest -v test_preview_target_security` tests the migration URL guard completely offline. It checks exact reviewed target identity, dedicated Preview naming, required remote certificate and hostname verification, permitted channel-binding/system-trust parameters, rejection of weaker or repeated parameters, and the existing localhost-only rehearsal format. It does not connect to Neon, Supabase, Render or any real account.

`test_preview_tls_postgres.py` additionally requires `LIFEOS_TEST_DISPOSABLE_TLS_POSTGRES=1`, local PostgreSQL server binaries and OpenSSL. It creates a new temporary loopback-only cluster, temporary CA and synthetic SQLite backup; it checks TLS and required channel binding, refuses a wrong hostname or CA and non-TLS connection, verifies a guarded migration, refuses a populated target, performs a TLS `pg_dump`/restore and restarts the local app against both copies. It also checks `sslrootcert=system` with an `SSL_CERT_FILE` override for a temporary trusted or untrusted CA. This does not establish Render's actual system trust store, Neon/Supabase compatibility, managed recovery, real redeploys or any provider's policies. Never aim this test at an existing server.
